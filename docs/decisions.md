# Decisions and departures

Each entry: the decision, why, the evidence, and what it costs. Departures from
`NEM_Event_Intelligence_Agent_Design.md` or the implementation prompt are marked **Departure**.

## D1. AEMO market event reports are not in the corpus (**Departure**)

- The design lists AEMO market event reports as a RAG source. Every aemo.com.au HTML page, including the
  market-event-reports listing and the copyright-permissions page, answered HTTP 403 with a Cloudflare
  browser challenge to scripted access (and to the WebFetch tool) on 2026-09-23. The results are recorded in
  `data/source_selection.json → host_checks`.
- AEMO media-library PDFs (`https://www.aemo.com.au/-/media/...`) *were* reachable when requested with a
  User-Agent. Their URLs cannot be discovered from the blocked listing pages, so the probe only accepts
  candidate URLs that answer 200 with `%PDF-` magic bytes. One guessed URL was rejected (403).
- **Instead**, the corpus uses (a) 5 validated AEMO PDFs covering demand definitions, load forecasting,
  dispatch and pre-dispatch; (b) the AEMO MMS Data Model Report pages on NEMWeb for the tables used; and
  (c) **AEMO market notices** from NEMWeb (`Reports/Current/Market_Notice`), which are official AEMO
  communications with a creation time, a notice type and usually a region.
- Market notices are labelled as *market notices*, never as *market event reports*. A notice may appear under
  `published_findings` only when its region and date match the investigated event, and only as a statement of
  what the notice says. No notice fetched for the primary event states a cause for the 31 Jul 02:35 SA1 price,
  so the system must not present one as an explanation.
- Cost: no post-event causal analysis from AEMO is available for any selected event. The system reports this as
  missing evidence.

## D2. Publisher files are fetched at setup, not committed

- AEMO's copyright page could not be re-read (403, see D1). The prompt allows committing excerpts only after
  checking the terms. The only first-hand statement retrieved is in the *Demand Terms in EMMS Data Model* PDF
  (p.2): "The material in this publication may be used in accordance with the copyright permissions on AEMO's
  website." NASA POWER asks to be notified of redistribution.
- So the repo commits code, the selection metadata (URLs, SHA-256, timestamps) and outputs generated by the
  code. `make data` / `make index` download the publisher files into git-ignored folders.
- **Risk:** market notices exist only in NEMWeb *Current*, which has rolling retention (~60 days observed:
  25 Jul–23 Sep 2026). The notices for the July events will roll off around late September 2026. After that, a
  fresh clone cannot re-fetch them. The retrieval tool then reports "notice no longer available from
  publisher" as missing evidence, and evaluation cases that need those notices are counted as
  `corpus_unavailable`, never as passes. The AEMO archives used for prices and demand are kept by NEMWeb for
  about 13 months (observed listings start Aug/Sep 2025).
- **User action to remove the risk:** if you check AEMO's copyright permissions in a browser and they allow
  redistribution with attribution, you can commit the small notice text files from
  `data/raw/MARKET_NOTICE/`, with this attribution.
- **Post-roll-off behaviour was simulated end to end** (every Current URL returning 404): setup, data-check, index,
  demo, eval and the full test suite all exit 0. Reports name the missing notices, notice questions abstain,
  and rolled-off Current files that AEMO later archives are recovered by name with a SHA-256 check.
  Details and observed output: [`docs/data-retention.md`](data-retention.md).

## D3. Price source: DispatchIS for timelines; Public_Prices only for the event scan

- DispatchIS (`Reports/Archive/DispatchIS_Reports`, daily archives of 288 five-minute files) supplies
  `DISPATCH/PRICE` (RRP, PRICE_STATUS, INTERVENTION) and `DISPATCH/REGIONSUM` (TOTALDEMAND, AVAILABLEGENERATION,
  DEMANDFORECAST, DISPATCHABLEGENERATION, NETINTERCHANGE). Each file has its own AEMO creation time, so each
  price has a provable publication time for as-of use.
- The next-day `Public_Prices` report is used only by the probe to scan 60 days for candidate events. The probe
  cross-checks the peak RRP against DispatchIS (all 8 events match exactly).
- The price series uses `INTERVENTION = 0` records. Intervals where AEMO also published an `INTERVENTION = 1`
  record are flagged. The project makes no claim about intervention settlement rules.
- Price revisions (`DISPATCH_PRICE_REVISION`) are not ingested. `PRICE_STATUS` (FIRM / NOT FIRM) is shown instead.

## D4. Publication time and as-of availability policy

- `issued_at` for a forecast run = `LOAD_DATE`, defined in the MMS Data Model Report as "Date time this forecast
  was produced". `published_at` = the AEMO C-header creation time of the file, which the probe checked equals
  the file-name timestamp for every run.
- A CSV timestamp alone does not prove when the file became public. The probe therefore measured the gap
  between creation time and the NEMWeb Current listing time over 2,879 forecast files and 2,880 actual files:
  p50 ≈ 4.6 min, p99 ≈ 37 min, max 165 min. The listing time can only overstate the true lag (a re-upload
  shows a later time), so taking the maximum is conservative.
- **Rule:** `available_at = published_at + 166 min` for operational-demand files. An as-of query uses only
  rows with `available_at ≤ as_of`. The response shows how many runs were excluded only because of this margin.
- Dispatch prices: the file for the interval ending *T* is created at the *start* of that interval
  (e.g. 00:00:11 for *T* = 00:05). The Current listing shows a lag of up to 52 min after interval start, so
  `available_at = interval start + 53 min`.
- NASA POWER data has no provable release time. Its `available_at` is the project's retrieval time, so it can
  never be used in a contemporaneous (as-of) view of a past event.

## D5. POE10/POE90 are AEMO-published, derived values, not project quantiles (**Departure** in wording)

- The design says "a published point forecast is not a P10/P90 estimate". The actual
  `PUBLIC_FORECAST_OPERATIONAL_DEMAND_HH` files carry `OPERATIONAL_DEMAND_POE10/50/90`.
- AEMO SO_OP_3710 (Load Forecasting, v25, 30 May 2023) states that "The 10% and 90% POE forecasts are derived
  from the 50% POE forecast … by multiplying the 50% POE forecast by a scaling factor."
- **Rule:** forecast-error metrics use POE50 only. POE10/POE90 are displayed as *AEMO-published POE values*,
  with the SO_OP_3710 caveat, never as calibrated intervals and never as this project's quantiles.

## D6. Event selection and storage bounds

- The probe scans the daily Public_Prices files available on NEMWeb Current (60 days). A candidate is a
  region-day whose maximum RRP is at or above the **project analysis threshold of 300 $/MWh**; a low-price
  candidate has an RRP below 0. These thresholds are not AEMO incident labels.
- Window = the peak interval ± 12 h, rounded to half-hours. Rules: prefer SA1 for the primary event; at most
  3 events per region; no overlapping windows in the same region; the window must be covered by archived
  DispatchIS and weekly forecast/actual archives (Current-only files expire).
- The high-price SA1 evening of 30 Jul (875 $/MWh at 17:20) falls inside the primary window, so it is part
  of the primary investigation rather than a separate event.
- Forecast runs kept: those created up to 48 h before the window start. This bounds storage; longer-lead runs
  exist in the archives but are not ingested.

## D7. Interval join policy (5-minute ↔ half-hour)

- All AEMO timestamps are interval-*ending*. A 5-minute interval (t−5, t] belongs to the half-hour (T−30, T]
  where T is the first half-hour boundary ≥ t. Boundaries in UTC+10 fall on UTC half-hours.
- Native resolutions are kept in tables and charts. Any derived half-hour price is labelled
  "derived: mean of 6 dispatch prices" and is only used for display alignment, never compared as if it were
  published by AEMO.
- `DISPATCH/REGIONSUM.TOTALDEMAND` ("Demand (less loads)", 5-min, scheduled-demand family) is never compared
  with operational-demand forecasts. The verifier and the tools refuse that pairing.

## D8. Runtime: Python ≥ 3.12 (**Departure** from the prompt's "3.11+")

- The Codespace default is Python 3.14.2; the pinned `numpy` 2.5.3 requires Python ≥ 3.12, so declaring 3.11 would
  be false for the locked environment. `requires-python = ">=3.12"`. Verified: `requirements.lock` installs on the
  Codespace's Python 3.12 and 72 tests pass there (`tests/time`, `tests/tools`, parser, validation, approvals,
  provider). The full suite ran on 3.14. CI runs 3.12 and 3.14 (unverified until GitHub runs it).

## D9. Weather context point

- NASA POWER hourly data is requested for one documented point per region (the capital city), in UTC, with
  T2M, WS50M and ALLSKY_SFC_SW_DWN. It is labelled retrospective, model-derived context for one location, not a
  regional average and not the forecast available at the time.

## D10. HTTP politeness toward NEMWeb

- Bursts of parallel requests produced transient HTTP 403s from nemweb.com.au. The client allows at most 3
  concurrent requests with ≥0.3 s spacing and retries 403 from that host with exponential backoff. A 403 that
  persists after the retries is reported as a failure, never ignored.

## D11. Embedding model: model2vec static embeddings (no torch)

- `minishlab/potion-retrieval-32M` at pinned revision `6fc8051fab2a1e0ee76689cf08c853792ac285e7` (MIT licence),
  a static embedding model distilled from a sentence transformer. It runs with numpy, which keeps the Codespace
  install small (no torch). It is a neural-distilled embedding model; the fallback (hashed TF-IDF + SVD, used
  only if the download fails) is labelled `lexical-svd-fallback` in the index manifest and never called neural.
- Static embeddings weaken on long chunks. Each chunk therefore also gets per-sentence vectors, and its dense
  score is the max. A deterministic rerank adds query-term coverage and a definitional-sentence bonus for
  definition-style questions. There is no learned reranker.

## D12. Document eligibility and publication times

- Event-specific documents (market notices) are eligible only for queries scoped to a matching region and window
  (±1 day, market-time dates); region-less notices (e.g. NEM-wide "prices subject to review") are never region
  findings. Only notices dated inside the window become `published_findings`.
- Publication times: notice "Creation Date" (market time); PDFs use the later of the stated effective/month date
  (a month means the end of that month) and the PDF modification date; the MMS Data Model Report uses its
  "Published by: AEMO dd/mm/yyyy" date (end of day). Unknown publication time → ineligible in as-of views.

## D13. Retrieval gold set scope

- 15 queries / 21 labelled (doc_id, snippet) items, hand-reviewed against chunk text on 2026-09-23. That is small, so
  the Recall@5 number is indicative only. Relevance is keyed on verbatim snippets rather than chunk ids, so the
  labels survive re-chunking.

## D14. Separate quantile experiment scope

- The design asks for an optional anomaly or quantile model on public demand and weather. Enough chronologically
  valid data exists: ~13 months of AEMO next-day actuals (ACTUAL_DAILY archives + Current) and NASA POWER T2M.
  So a small **linear quantile regression** (numpy, pinball loss) was fitted for SA1 day-ahead demand. Forecasts
  are issued at 12:00 NEM on D-1, with lags ≥ 2 days, calendar terms and 2-day-lagged temperature; target-day
  weather is never used. Training targets are limited to days ≤ first test day − 2 (published before the issue
  time). Six monthly rolling-origin folds, compared with seasonal-naive and persistence baselines.
- It is kept separate from the investigation app and is never shown as an AEMO forecast. It is not compared with
  AEMO's POE50, because only event-window forecast runs were ingested (D6).

## D15. CI and hosted checks are written but UNVERIFIED

- `.github/workflows/ci.yml` needs no secrets. It fetches real data (publisher files are not committed), caches
  `data/raw` and the embedding model, and runs lint, mypy, tests, offline eval and the safety suite on 3.12 and
  3.14. It has not run on GitHub from this session. Possible failure points: publisher throttling or Cloudflare
  towards GitHub runner IPs, and notice roll-off (handled as missing evidence, not a failure).
- The live controller was exercised only through a fake transport and a mock-HTTP SDK contract test. The default
  model id `gpt-5-mini` is a placeholder to be set via `NEM_AGENT_MODEL`.
- *Update 2026-09-25:* the hosted smoke test has since run with a real key (D18, `docs/progress.md` Post-PR);
  the 40-case hosted evaluation is still UNVERIFIED.

## D16. Version stamping

- Each report records `versions.code` (git short sha, `-dirty` if tracked **or untracked** files differ from HEAD),
  `data` (store content hash), `corpus` (chunk hashes + embedder), `prompt` (`prompts/v1`, `prompts/v2` since 2026-09-25; old versions are kept), `model` and `controller`.
  Until this work is committed, reports correctly say `a8199ec-dirty` (the initial commit does not contain this code).

## D17. Identity of API responses (found by the clean-checkout run)

- The first fresh-clone `make data` re-downloaded all 8 NASA POWER responses and **rejected every one** as a SHA-256
  mismatch. The JSON carries `times.data` (the server's processing time), which changes on every request, while
  the parameter values were identical. The build correctly refused unverified bytes, but the clean checkout then
  had no weather rows.
- **Rule:** publisher *files* (NEMWeb archives, PDFs, notices, HTML) keep strict byte identity. For API datasets
  with known volatile keys (`NASA_POWER_HOURLY`: `times`), the selection also records `content_sha256`, the hash of
  canonical JSON without those keys, computed from the originally probed bytes (whose raw SHA-256 was re-checked).
  A re-download is accepted if either hash matches. The cache metadata records which hash verified it.

## D18. Live synthesis contract and notice clock times (from the first hosted run, 2026-09-25)

- **Context over leniency.** The first gpt-5-mini narrative failed validation because the model was not told
  things it needed. The fix was to give it that context, not to accept its output. Every number the model may state
  now has its own evidence id: the analysis threshold is registered by the tools, and counts carry units.
  Constraints stripped from strict schemas are restated in descriptions. Findings are rendered by the controller
  from the cited verbatim quote, and the model chooses only which citation. Replay already worked this way.
- **Notice times are NEM market time (UTC+10).** Notices write "HHMM hrs" without a zone. Checked against
  publication timestamps for all 13 "At HHMM hrs" notices in the corpus:
  - UTC+10 fits all 13 (10 published up to 6 h after the stated time, 3 "short notice outage" notices published
    2–17 min before it).
  - UTC+09:30 fits 2 of 13, and UTC fits none.

  Retrieval returns each notice's `clock_times` with UTC and region-local equivalents, so times are never
  compared across bases by eye.
- **NETINTERCHANGE sign.** AEMO: "Net interconnector flow from the regional reference node" (MMS Data Model), and
  AEMO's Demand Terms worked example pairs a negative NetInterchange with a net import. The price timeline states
  the definition and a code-computed direction.
- **Validator changes are limited to consistency fixes, each with a test that real numbers are still caught.**
  - Issued chunk ids are removed only on an exact match.
  - U+2010/U+2011 hyphens are treated as "-".
  - DD/MM/YYYY dates use strict ranges.
  - `°C` is the same unit as `C`.
  - One check is stricter: `FINDING_NOT_QUOTED`.
  - "HHMM hrs" times and equipment numbers outside quotes stay flagged.
- **Two of the eight model calls are reserved** for synthesis and one repair (a run used all 8 in one-tool-per-turn
  loops). The single-repair policy is unchanged.

## D19. Live budgets are always enforced (2026-09-25)

- The USD budget was enforced only if `NEM_AGENT_PRICE_*` was set, and `eval --budget-usd` applied per question.
  Now a dated price table in `config.py` (gpt-5-mini: 0.25 / 2.00 USD per 1M input/output tokens, from the OpenAI
  pricing page, 2026-09-25; environment override) makes every session budget enforceable. A model with no price is
  refused before any request.
- Costs charge cached input at the full rate, so they are upper bounds. The check runs before each model call, so
  a session can overshoot by at most one call.
- `eval --mode live` estimates the run before starting (38 model questions: 1.90 USD typical, 5.70 USD high from
  live-smoke runs). It refuses when the estimate exceeds `--budget-usd`. The budget is run-wide: each question gets
  only what remains, and a run that uses it all is written as incomplete with no metrics. Live results go to
  `artifacts/eval/live*.json`/`live_report.md`, never over the offline `report.md`.


## D20. Publisher revisions are re-pinned after review, never accepted automatically (2026-09-25)

- **What happened:** the first CI run on `main` (run 36107168395, after PR #1 was merged) had no cache and
  downloaded everything. Three pinned sources had changed upstream since they were pinned on 2026-09-23:
  - `aemo_so_op_3705`: AEMO replaced SO_OP_3705 Dispatch **Version 97** (effective 1 April 2026) with **Version
    98** (effective 23 September 2026) at the same URL. `Last-Modified` is 2026-09-23T09:38:32Z, three hours
    after our pin; the file is 1,315,253 bytes (was 1,267,581). Version 97 is no longer served there.
  - `nasa_power_tas1_20260805_20260806` and `nasa_power_vic1_20260819_20260820`: NASA POWER replaced
    provisional **GEOS-IT** meteorology with final **MERRA-2**. All 48 hourly T2M and WS50M values changed;
    ALLSKY_SFC_SW_DWN is unchanged. The six July responses were already MERRA-2 when pinned and still match.
- **Why the index step failed:** `build-index` exits 1 when `failed_sources` is non-empty or no chunks were
  built. A checksum mismatch is a failed source, so SO_OP_3705 alone caused the failure. Rolled-off market
  notices are counted separately (`rolled_off_sources`) and never change the exit code; the run reported 12 of
  them as missing evidence, as intended. `build-data` fails only for core datasets (DISPATCHIS and the two
  operational-demand datasets), so the NASA mismatches were reported but did not stop the job.
- **Rule:** a mismatch stays a failure. Verification is unchanged: raw SHA-256 for files, and the canonical
  content hash for API responses, whose bytes always differ. The only way to move a pin is
  `scripts/repin_source.py`:
  - it takes a reviewer-supplied hash and refuses unless the content served now matches it;
  - it keeps the old pin in the entry's `superseded` history, with what the publisher changed and why;
  - it regenerates `data/SOURCES.md`.

  Machines holding the old content fetch the new version automatically, because the old copy no longer matches
  the pin.
- **Why re-pin rather than keep the old version:** the old bytes cannot be downloaded any more, so pinning them
  would make every fresh setup fail. Both new versions were fetched twice with identical content; the NASA
  change is a one-way move to the final product.
- **Effect:** offline evaluation rows and metrics are unchanged. Retrieval Recall@5 went from 17/21 to 16/21:
  version 98 changed the keyword-search (BM25) statistics, and one LOR2 notice fell from rank 5 to just outside
  the top 5. Gold labels were not changed.
- **CI cache:** the `restore-keys: nem-raw-` fallback is removed. It restored caches from older pin sets, which
  brought back market notices that have since rolled off NEMWeb and hid the change. Caches are now reused only
  for the identical pin set, so a pin change always runs against what a fresh setup downloads.
- **Error messages:** a mismatch on an API source now shows the content hash and says the values changed, with a
  pointer to the re-pin procedure; the raw hash alone looked random on every run.
- **Inconsistent API servers (added 2026-09-27):** PR #2's first CI run failed although nothing had been revised.
  NASA POWER returned values different from the pin for 3 of the 16 NASA requests the two CI jobs made
  (`sa1_20260730`, `vic1_20260730`, `tas1_20260805`); the content hashes matched no version seen before. At the
  same time 32 of 32 requests from the Codespace returned the pinned values. In one job, a rebuild seconds later
  received the pinned content. A mismatching NASA response is therefore requested again, at most twice, 5 s
  apart. Only content equal to the pin is ever accepted. Each variant seen is logged (`checksum_mismatch_variants`
  in the raw manifest) and kept under `data/raw/_rejected/` for review. If every response differs, the source
  fails as before. Publisher files (AEMO, NEMWeb) are not retried.

## D21. Source governance: pinned builds and a separate publisher-refresh check (2026-09-27)

- **Two checks, two purposes.**
  - *Pinned build:* CI, `make data` and `make index` use only content whose hash matches the reviewed pin. It never
    substitutes other content.
  - *Publisher-refresh check:* `make refresh-check` and the weekly `publisher-refresh` workflow download what AEMO
    and NASA serve now into a staging folder. They report `unchanged`, `changed`, `inconsistent` or `unavailable`,
    and never touch the manifest, the raw cache, the store or the index.
- **Reports are for a human reviewer.** For each changed source:
  - old and new hashes;
  - safe HTTP metadata;
  - document version or NASA API metadata;
  - a content diff (PDF or HTML text lines, changed NASA values, changed zip members);
  - the affected data tables, index documents, events and evaluation cases;
  - with `--eval`, a sandboxed offline evaluation of the pinned set against the candidate set.
- **Accepting is explicit.** `scripts/repin_source.py` now requires `--approved-by`. With `--report`, it refuses
  unless the report lists the same change. It records the report hash, the version metadata, the approver and where
  the old bytes are kept. CI's `scripts/check_pin_changes.py` fails any pull request that changes a pin without
  such a history entry, or that edits history or adds or removes sources silently.
- **The application shows what it uses.** `/health`, `/sources`, the Streamlit sidebar and `nem-agent sources` list
  data and corpus versions and group sources as `pinned`, `revised` (in use pending review, or excluded) and
  `unavailable` (excluded). Builds record `pin_status` and `upstream` for every source. Excluded sources stay
  missing evidence, and nothing is substituted.
- **Market notices.** NEMWeb has `Reports/Archive/Market_Notice/`, but its listing had 0 files on 2026-09-27. Rolled-off
  notices are looked up there, accepted only on a hash match, and the observed listing is recorded. Earlier wording
  said "AEMO never archives notices"; that was stronger than the evidence.
- **Limits.**
  - Superseded bytes are kept only locally (`data/pinned_store/`, git-ignored). Publisher files are not
    redistributed (D2), and a GitHub Actions cache is not an archive.
  - A fully repeatable CI would need a durable private store of pinned bytes. That depends on AEMO's terms, which
    are the owner's decision.

## D22. Approved-bytes store for reproducible pinned builds (2026-09-27)

- **Problem.** Pinned builds downloaded from the publishers, so a pin became unobtainable when AEMO replaced a file
  (SO_OP_3705 Version 97), NEMWeb rolled notices off (67 of 198 by 2026-09-27), or NASA served inconsistent values.
  GitHub deletes an Actions cache unused for 7 days, so the cache is not an archive.
- **Decision.** Keep every approved version in a content-addressed store: assets of releases in this private
  repository, each named by its SHA-256. The index `data/pinned_store.json` in git records each object's URL, original
  retrieval time, the pin it satisfies (current or superseded), attribution, reuse terms and approval history.
  - CI restores only objects that hash to their key and match a current pin (`make restore-pinned`, strict), and
    fails if the build contacted a publisher.
  - The store is add-only: new releases, no `--clobber`, and the pin guard rejects removed or edited index entries.
  - Release immutability, which the owner switches on in Settings, locks assets once published.
  - Details and alternatives are in docs/pinned-store.md.
- **Licensing.**
  - *AEMO:* the general permission to use AEMO Material "for any purpose" with attribution (archived page,
    2026-09-23) covers a private, attributed store.
  - *NASA POWER:* states no restriction and asks for acknowledgement and notification.
  - D2 still keeps publisher files out of git, now for size and separation rather than licensing.
- **Recovery.** SO_OP_3705 Version 97 and the two provisional NASA responses were recovered from the 2026-09-23 CI
  cache (run 36357940231), verified against their superseded pins, and stored as `superseded` objects.
- **Not covered.** The embedding model (Hugging Face, pinned revision) and Python packages (PyPI, pinned versions)
  are still fetched from their services.

## D23. Bounded diagnostics of hosted-model calls (2026-10-03)

- **Problem.** Three of the four routing calls cut off in the Live check of the v12 routing extraction returned 912 to
  1,168 visible tokens, but a cut-off response's text was never kept, so the cause could not be told. The trace also
  named only the model requested, not the one that answered, or the reasoning effort applied. Both are needed before
  comparing models.
- **Decision** (`agent/diagnostics.py`, called from `LiveController._call`; recorded in the trace only):
  - **Settings, kept apart.** Each model-call event records `requested` (model, `max_output_tokens`, reasoning effort:
    "not sent" when the request sends none, so the provider's default applies) and `reported` (the same three as the
    response gives them; "not reported" when a field is absent). A failed call records `requested` only.
  - **A response that did not finish** gets a `<stage>:incomplete_output` event: the visible text's length, its first
    and last 300 characters (never overlapping), the whitespace share, the longest run of one repeated character and
    of one repeated line, the trailing whitespace, and the JSON field open at the cutoff.
    - **Cause:** "unknown" unless the visible text establishes it, as "whitespace at the cutoff" or "repetition at the
      cutoff" (a run reaching the cutoff that covers at least half the text and 200 characters). Token usage alone
      never sets a cause.
    - **Open field:** "established" only when the text is a valid JSON prefix that stops inside a value whose key is
      known; otherwise "uncertain", with the reason.
  - **Cost basis.** Each model-call event says what its `cost_usd` is: the ledger's accounting at the configured list
    prices, not the billed amount.
- **Unchanged.** A response that did not finish is still rejected before parsing (`_structured`, I-14), and nothing
  recorded here feeds an answer, a resolution or validation. No prompt, schema, cap, budget or validator changes. No
  request input, instruction or key is recorded: only the response's own visible output, bounded.
- **Cost.** Trace events grow by a few hundred characters per model call, and by at most about 1 kB per cut-off
  response.

## D24. Typed analytical results: the foundation, for demand maxima (2026-10-03)

Acceptance check recorded before implementation. A foundation change: it claims no improvement in Live answer quality.

- **Problem.** A result the code computes (the I-17 demand maximum) exists only as an untyped dict on the in-memory
  resolution and as a sentence in the summary. Its provenance is a private runtime field (I-21) that a JSON round trip
  loses, and nothing can tell a later reader whether a result in a saved or exported report is still what the pinned
  data gives.
- **Decision** (`results.py`; `agent/demand_max.py` produces it; one bounded PR):
  - **A versioned contract,** `AnalyticalResult` (`analytical_result/1`), kind `demand_maximum` only: status
    (`established`, `not_established`, `unavailable`), measure, metric, unit, region, window, cutoff, coverage
    (interval length, intervals in the window, held, complete, excluded by the cutoff), the maximum and its interval
    ends (ties kept), durable source-row IDs, deterministic limitations, and a digest of its content. An incomplete
    window gives no maximum: the highest value held is carried apart, as not a maximum. An unavailable result carries
    no value, only its reason.
  - **Identity:** `result_id` hashes the request (question and explicit fields, not the mode), kind, measure, region,
    window, cutoff, calculation version and the pinned data version; `computation_id` hashes the same without the
    request. Evidence IDs and the tool-call ID are in-run references, kept apart and outside the identity.
  - **Admission:** only the runtime verifier admits a result to the investigation's verified-result registry. In the
    run, it re-derives the result from the pinned store with the same tool code and checks the in-run evidence

    - the question parser and the model's span read differently;

       or question mark;
     - a **bound** forecast run's selection or half-hour words;

     matches something resolved: "after 02:35" must not pass as an event's 02:35 peak.

       vocabulary ("late in the day", "once the evening ramp began"), is not detected.
